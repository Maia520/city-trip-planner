# 城市出行游玩规划

> 输入"谁去、去哪、想玩什么"，输出三档可比较、走得完、标注不确定性的方案。

## 核心原则

1. **只输出有来源的真实地点** — 美食、街区、商场、营业时间、坐标必须来自地图 API、Web 检索或用户提供。查不到就标注"未核验"或放进备选区，禁止编造。
2. **年龄不是标签，是四个参数** — 体力预算、注意力、硬约束、决策权重。只看岁数排不出方案。
3. **组合人群取"最弱成员 × 经验系数"** — 不取平均。默认 0.85，熟练照护者 0.92；带 70 岁老人和 4 岁孩子时，强度由最弱者决定。
4. **聚类优先于排序** — 先用等时圈分半场，再在簇内排序。簇切错了，TSP 再优也是折返路线。
5. **硬约束一票否决，并说明原因** — 台阶、无障碍、排队、医疗、午休，命中即移出主方案，"为什么没排"比"排了什么"更能建立信任。
6. **ABC 不是好中差** — 三档是三种目标函数下的最优解，默认推荐 B 舒适版。
7. **留白与诚实** — 全天留 15%–25% 缓冲；每个点位给置信度与最后核实时间。

## 输入

| 字段 | 含义 | 默认 |
|------|------|------|
| `destination` | 目的地（城市/片区/地标） | 必填 |
| `party_size` | 总人数 | 由 members 求和 |
| `members` | 年龄结构：`[{band, count}]` | 按 `party` 推导 |
| `trip_type` | `local_halfday` / `local_fullday` / `day_trip` / `multiday` | `local_fullday` |
| `activities` | 预期活动标签（美食、街区、商场、博物馆、徒步、夜游等） | 空，按人群推荐 |
| `date` / `days` | 日期与天数 | 今天 / 1 天 |
| `budget_level` | `low` / `mid` / `high` | `mid` |
| `experience_level` | `novice` / `experienced`（熟练照护者安全系数 0.92） | `novice` |
| `mobility` | `normal` / `stroller` / `wheelchair` / `slow_walk` | `normal` |
| `must_visit` | 必去清单（硬保留，作锚点） | 空 |
| `weather` / `health_flags` | 天气、健康限制 | 未知 / 空 |
| `start_time` / `end_time` | 时间窗 | 09:30–21:00 |

年龄段可用 `0-3`、`4-6`、`7-12`、`13-17`、`18-25`、`26-35`、`36-50`、`51-60`、`61-70`、`70+`，也可用 `A1`–`A10`。

缺失项用默认值并**显式告知用户**。细节见 `references/intake-and-data-sources.md`。

## 工作流

### Phase 1：需求结构化（Intake）

提取人数、年龄结构、目的地、预期活动、时间窗、预算、体力/无障碍、必去、天气、健康限制。缺失项用默认值并说明。

### Phase 2：确认真实数据源（Grounding）

优先用 `scripts/fetch_pois.py` 取真实 POI：有 `AMAP_KEY` / `BAIDU_MAP_AK` 时走高德/百度，无 key 时回退 Photon/OSM。每个点位记录 `source`、`verified_at`、`confidence`。三源都拿不到时，只输出检索框架，**不虚构店铺**。
详见 `references/intake-and-data-sources.md`。

### Phase 3：年龄与组合强度解析（Profile）

读 `references/age-profiles.md`：把每位成员翻译成体力、注意力、硬约束、决策权重；组合人群取"最弱成员 × 经验系数（0.85/0.92）"。
同时含 0–6 岁与 70+ 时，触发多代同游专项：点位 A4/B3/C2、缓冲 ≥30%、12:00–14:30 强制 90 分钟午休、超过 1.2 km 打车。硬约束（台阶、无障碍、母婴室、午休、排队、医疗）在此阶段直接过滤候选点位。

### Phase 4：三分类 POI 召回（Recall）

分别召回 **美食**、**市井街区**、**商场**，标注 `tier`（core / normal / optional）、`indoor`、`has_stairs`、`step_count`、`queue_min`。
按距离分层与年龄适配筛选；用"烟火气六维"识别真街区。商场是基础设施，不是"要逛的景点"。
详见 `references/poi-selection.md`。

### Phase 5：等时圈聚类与路线装配（Assemble）

```bash
python "$SKILL_ROOT/scripts/plan_route.py" --input itinerary.json --output route.json
```

脚本负责：组合强度、距离与耗时、锚点聚类、簇内开放 TSP、时间窗装配、硬约束告警、ABC 三档生成与对比。
Agent 负责：锚点语义判断、停留时长、活动玩法版本、路线叙事与取舍解释。
算法见 `references/route-planning.md`。

### Phase 6：ABC 三档与对比（Variants）

读 `references/plan-variants.md`：A 尽兴版（体验最优）、B 舒适版（默认推荐）、C 省心版（低预算低风险，雨天/体力不足优选）。
三档必须给同一组硬指标对比，并各写一句"用 X 换 Y"。

### Phase 7：时段微调与 B 计划（Validate）

按 `references/route-planning.md` 的时段策略表微调：商场落正午/末端、夜景落傍晚、预约场馆落开门首小时。
生成主方案 + 雨天版 + 夜间版 + 体力降级版；核对四个数字。

### Phase 8：输出与二次确认（Deliver）

按 `assets/route-output-template.md` 输出。必须包含：**总步行距离、爬升/台阶、缓冲时长、最晚返程时间**；ABC 对比表；排除理由；每点置信度；出行前二次确认清单。
边界与免责见 `references/output-and-boundaries.md`。

## ABC 分档速查

| 档位 | 名称 | 适合谁 | 点位 | 步行 | 室内占比 | 撤退难度 |
|------|------|--------|------|------|----------|----------|
| A | 尽兴版 | 体力好、无老人幼儿、想玩透 | 5–7 | 8–12 km | 20%–30% | 高 |
| B | 舒适版（推荐） | 大多数家庭、带娃/带老人 | 3–4 | 5–7 km | 30%–40% | 中 |
| C | 省心版 | 雨天、高温、体力不足、只想散心 | 2–3 | 3–5 km | ≥50% | 低 |

## 决策规则

| 场景 | 处理 |
|------|------|
| 只给目的地，没给人数/年龄/时间 | 按 2 名成人、一日游、09:30–21:00 规划，并列出可改参数 |
| 含 0–3 岁或 70+ | 强度按最弱成员 × 经验系数；12:00–14:30 不排程；必给室内备选 |
| 多代同游（0–6 + 70+） | 点位 A4/B3/C2；超过 1.2 km 打车；午休写入时间轴；给"分头行动 + 汇合点" |
| 经常带老人孩子（experienced） | 安全系数 0.92，但硬约束不放松 |
| 用户给必去清单 | 硬保留并作锚点，其余点围绕它排 |
| 雨天/高温 | C 档升为主推，商场主场，街区只留精华段 |
| 外地旅游 | 首末日轻安排；少点位高确定性；给撤退路线 |
| 数据只有单一平台且超过 6 个月 | 标"待核验"，放备选区，不进主路线核心 |
| 检索不到真实店铺 | 输出"检索框架 + 待确认清单"，不编造 |

## 安全与合规约束

- **禁止**编造真实店名、地址、评分、营业时间、排队时长，或把测试数据当作生产结果。
- **禁止**承诺实时排队、实时路况、订座订票；只能给风险等级与最晚决策时间。
- **禁止**替代导航；只输出路线骨架，落地导航交给地图 App。
- 医疗、无障碍、高原/海边/山区只给风险提示与就医路径，不给医学结论，不作绝对担保。
- 行程不替代监护；儿童、老人、认知障碍者的走失、跌倒、突发疾病由监护人负责。
- 抓取点评/地图内容时优先官方 API；评价只做聚合统计，不逐条复制，遵守平台条款。
