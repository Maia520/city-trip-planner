# 路线规划方法论

## 1. 四条组织原则

1. **地理聚类优先于评分排序** — 先按邻近分组，再在组内排序。这是"不走回头路"的结构性保证。
2. **硬时间约束先于软偏好** — 闭馆时间、预约时段、末班车、演出场次不可谈判；"最佳拍照时段""饭点"可谈判。
3. **体力曲线匹配日程形状** — 上午峰值安排高强度；午后低谷安排低强度（商场、咖啡馆、博物馆、游船）；傍晚回升安排夜景街区。
4. **留白优于塞满** — 午间留 1 小时、全天留 15%–25% 缓冲。

## 2. 组合强度计算

```text
party_walk_factor = min(各成员 walk_factor) × 经验安全系数
                   （novice 0.85 / experienced 0.92）
party_buffer      = max(各成员 buffer_ratio)
party_queue       = min(各成员 queue_tolerance_min)
hard_constraints  = union(各成员 hard_constraints)
有效步行上限       = max_walk_km × party_walk_factor × 档位系数
```

档位系数：A 1.30、B 1.00、C 0.75。

**不取平均，取最弱成员的下限再打折。** 例：2 名 36–50 岁 + 1 名 7–12 岁 + 1 名 61–70 岁，最弱为 61–70（0.67），novice 组合系数 = 0.67 × 0.85 ≈ 0.57；experienced 为 0.67 × 0.92 ≈ 0.62。基准 6 km 时，有效上限约 3.4–3.7 km。

若组合同时含 0–6 岁与 70+（多代同游），除"最弱成员"规则外，还需触发专项收紧：点位上限 A4/B3/C2、缓冲下限 30%、12:00–14:30 强制 90 分钟午休、超过 1.2 km 打车、A 档最多上浮 10%。

若组合含 0–3 岁、61–70 或 70+，A 尽兴版必须标注"不建议全员参加"，并给分线方案。

## 3. 五步算法

### 第一步：锚点选择（Anchor Selection）

从候选中选 1–3 个"不可替代"的锚点：地标景区、必吃餐厅、目标街区。`must_visit` 与 `tier=core` 优先作为锚点。

### 第二步：地理聚类（Clustering）

以步行/骑行等时圈而非直线距离聚类（直线 800 m 可能因河流、快速路变成 1.5 km）。

- 有锚点：每个非锚点分配给最近锚点；超出等时圈半径的点**另起一簇**，不硬并。
- 无锚点：按半径阈值（默认 1.5 km）并查集合并。
- 每个簇视为一个"半场"；单簇超过 8 个点时告警，建议拆分。

### 第三步：簇内排序（开放路径 TSP）

- n ≤ 10：Held-Karp 动态规划，O(2^n·n²)，毫秒级；
- n > 10：最近邻构造 + 2-opt 局部搜索。

目标是**开放路径**（起点终点可不同），游客不需要回到原点。簇内排序必须固定簇的起点为"离上一站最近的点"，否则会把最近的门口留到最后，制造无效折返。

### 第四步：时段装配（Time-window Assembly）

```text
到达时间 + 停留时长 + 缓冲 ≤ 下一站最晚可进入时间
```

不满足则三种修复之一：交换顺序、替换同簇备选、降级为"可选加购点"。

### 第五步：局部优化（Local Search）

跨簇交换点位，只接受"总步行距离下降且时间窗仍满足"的移动。首版可先省略，优先保证聚类与时间窗正确。

## 4. 时间预算模型

```text
T_total = Σ(停留时长_i) + Σ(位移时长_j) + Buffer

位移时长_j = 路网距离_j / 速度 + 换乘惩罚
  · 步行 4.0 km/h（约 80 m/min）
  · 打车 22 km/h + 5 min 等位，拥堵系数 1.2–1.5
  · 地铁 8 min 换乘惩罚

Buffer = party_buffer + 档位增量 + trip_type 增量 + 午休保护区
  · A 尽兴版 -0.05，B 0，C +0.10
  · 0–3 岁 / 70+ 基础缓冲 0.35
  · 多代同游：12:00–14:30 插入 90 分钟午休段，写入时间轴
```

参数建议（经验值）：

- 单点停留 45–90 分钟；餐饮 60–90 分钟；
- 单日核心点：本地 3–4 个、外地 2–3 个；
- 单日步行总量：见 `references/age-profiles.md` 画像表。

## 5. 时段策略表

| 时段 | 推荐内容 | 规避 |
|------|----------|------|
| 08:00–10:30 | 需排队/需预约的点位（开门首小时人流最低） | 过早的街区（店铺未开） |
| 10:30–12:00 | 街区漫步、小店逛 | 正午暴晒路段 |
| 12:00–14:30 | 午餐 + 商场/咖啡馆休息（体力低谷，**不可排程保护区**） | 连续转场 |
| 14:30–17:00 | 博物馆、室内场馆、次核心点位 | 夏季户外长距离步行 |
| 17:00–19:00 | 日落机位、江边/城墙、晚餐 | 饭点热门店（等位 40 分钟+） |
| 19:00–22:00 | 夜景街区、夜市、灯光秀 | 背街小巷（安全） |

含 0–6 岁、61+ 或 70+ 时，12:00–14:30 为硬性不排程；其余人群可作为"建议休息"。

## 6. 本地与外地旅游

| 维度 | 本地 / 一日游 | 外地 / 多日游 |
|------|---------------|---------------|
| 决策成本 | 低，容错高 | 高，沉没成本大 |
| 体力分配 | 单日爆发 | 连续累积，第三天最危险 |
| 交通接驳 | 30 分钟内 | 落地 2–4 小时 |
| 景点密度 | 2–4 个，可临时增减 | 每天 2–3 个，需预约 |
| 打卡 vs 深度 | 可出片优先 | 体验优先 |
| 风险 | 低，可随时回家 | 高，必须有撤退路线 |

**底层差别是"退出成本"。** 本地默认"探索模式"；外地默认"保障模式"（少点位、高确定性、强预案）。外地首日与末日轻安排，落地后 3 小时设计为低强度缓冲段。

## 8. B 计划

主方案之外必须给：

1. **雨天版**：商场为主场，街区保留可快速穿行的精华段；
2. **夜间版**：夜景街区 + 夜市，避开背街；
3. **体力降级版**：砍掉最远/最累的点，改为"就近 + 久坐"；
4. **人流降级版**：热门点换成同带位备选，或错峰到开门首小时。

每个版本都要能回答："如果下雨/排队/老人走不动，改去哪？"

## 9. 十类常见坑

1. 被网红攻略带偏 → 优先采信缺点描述充分的攻略。
2. 忽略营业/闭馆时间 → 营业时间作为硬约束前置校验。
3. 忽略交通耗时 → 按路网距离算，加换乘惩罚与拥堵系数。
4. 节假日人流 → 自动降级热门点权重，给错峰版本。
5. 天气 → 每个半天配一个室内替代。
6. 门票与预约 → 输出"预约提醒"与"最晚决策时间"。
7. 动线折返 → 用等时圈而非直线距离聚类。
8. 强度误判 → 最弱成员 × 经验系数（0.85/0.92）+ 分档系数。
9. 回程没兜底 → 明确"最晚返程时间"，末日不排重行程。
10. 只给一条路 → 主方案 + 2 个局部替换 + 1 个整体降级。

## 10. 脚本用法

```bash
# 默认输出 ABC 三档
python "$SKILL_ROOT/scripts/plan_route.py" --input itinerary.json --output route.json

# 只要单档（B 舒适版）
python "$SKILL_ROOT/scripts/plan_route.py" --input itinerary.json --plans 1
```

输入 JSON 关键结构：

```json
{
  "options": {
    "start_time": "09:30",
    "end_time": "21:00",
    "trip_type": "local_fullday",
    "members": [
      {"band": "36-50", "count": 2},
      {"band": "61-70", "count": 1}
    ],
    "activities": ["food", "street", "mall"]
  },
  "pois": [
    {
      "id": "p1",
      "name": "真实点位名称",
      "lat": 30.67,
      "lng": 104.06,
      "category": "street",
      "tier": "core",
      "dwell_min": 60,
      "open_time": "10:00",
      "close_time": "22:00",
      "confidence": "verified"
    }
  ]
}
```

输出包含 `comparison`（三档对比）、`plans[]`（每档的 summary/segments/warnings/unassigned），以及四个关键数字：`total_walk_km`、`buffer_min`、`return_deadline`、`within_window`。

> 脚本只做确定性计算，不生成任何真实 POI。输入点位必须由 Phase 2 的真实数据源提供。
